# TypeScript setup NestJS depends on

Nest is not "TypeScript with decorators as sugar". Its dependency injection reads type information that **the compiler emits at build time**. Get the compiler options wrong and the app compiles, typechecks, passes hermetic tests, and fails at boot.

## The non-negotiable compiler options

```jsonc
{
  "compilerOptions": {
    "experimentalDecorators": true,   // legacy TS decorators — required
    "emitDecoratorMetadata": true,    // writes design:paramtypes — DI depends on it
    "target": "ES2023",
    "module": "nodenext",             // or "commonjs" for a CJS project
    "strictNullChecks": true
  }
}
```

And, once, at the very top of the entry file — before any decorated class is loaded:

```ts
import 'reflect-metadata';
```

`@nestjs/core` imports it too, but relying on that makes the ordering an accident of import graphs. A standalone script that constructs a decorated class without going through `NestFactory` will throw `Reflect.getMetadata is not a function` if nothing imported it.

## Why `emitDecoratorMetadata` is load-bearing

With it on, this constructor:

```ts
@Injectable()
export class OrderService {
  constructor(private readonly repo: OrderRepository) {}
}
```

compiles to JavaScript that additionally records `design:paramtypes = [OrderRepository]`. Nest reads that array to know what to inject. Nothing in the `.ts` source is consulted at runtime — only the emitted metadata.

Three things erase or corrupt that array. Each is covered where it bites:

- an `import type` on the injected class → [dependency-injection.md](dependency-injection.md)
- an **interface** as the parameter type — interfaces do not exist at runtime, so the emitted entry is `Object`; use a token (`@Inject(TOKEN)`) instead
- a missing `@Injectable()` (or any other) decorator on the class — with no decorator on the declaration, TypeScript emits no metadata for it at all

## TC39 / Stage-3 decorators are not supported

TypeScript 5 shipped the standard decorator proposal, and it is tempting to drop `experimentalDecorators`. Do not.

The Nest maintainers' position on the tracking issue ([nestjs/nest#11414](https://github.com/nestjs/nest/issues/11414)) is that support waits on *"metadata support & parameter decorators"* — standard decorators have **no parameter decorators at all**, and Nest uses parameter decorators (`@Inject`, `@Param`, `@Body`, `@Query`) everywhere. The design-time type emission is gone too: TypeScript's own open issue on the subject states that *"after the implementation of the [TC39 decorators] in TypeScript 5.0 the ability to emit design-time type information has been lost unless we keep using the experimental (legacy) decorators system"* ([microsoft/TypeScript#57533](https://github.com/microsoft/TypeScript/issues/57533)).

The practical confirmation: the ESM project template generated by NestJS 12 — the newest artifact the project ships — still sets both legacy flags ([migration guide](https://docs.nestjs.com/migration-guide)).

## ESM or CommonJS

As of v12 the core packages **ship as ESM**, and `nest new` asks which layout you want. Your own application does not have to follow:

- **Staying CJS is supported and is not a migration debt.** The migration guide is explicit that moving your app to ESM *"is entirely optional and not part of upgrading to v12"* — Node's `require(esm)` bridges the gap.
- **Going ESM** means `"module": "nodenext"`, `"type": "module"` in `package.json`, and relative imports carrying explicit extensions. Apply that consistently: a half-migrated import graph breaks at runtime, not at compile time.
- `require.main === module` does not exist under ESM. The bootstrap guard becomes `import.meta.url === pathToFileURL(process.argv[1]).href`.

## `verbatimModuleSyntax` and friends

`verbatimModuleSyntax` makes the emitted import list literal: *"any imports or exports without a `type` modifier are left around. Anything that uses the `type` modifier is dropped entirely"* ([TS docs](https://www.typescriptlang.org/tsconfig/verbatimModuleSyntax.html)). That is exactly the mechanism behind the DI trap in [dependency-injection.md](dependency-injection.md) — with it on, a `type`-modified import is *guaranteed* to be erased, so a DI parameter typed off it is guaranteed to break.

It is safe to enable; what is unsafe is letting a lint autofix decide which imports get the modifier.

## The TypeScript 7 trap (current as of 2026-09-06)

TypeScript 7.0 (released 2026-07-08) is a native rewrite that **does not expose the programmatic Compiler API**. `nest build` and `nest start` use that API, so with `typescript@7` installed they fail — for both the default `tsc` builder and the SWC builder. The tracking issue is open ([nest-cli#3479](https://github.com/nestjs/nest-cli/issues/3479)); the shipped mitigation so far is only a clearer error message telling you to install TypeScript 6.

Until it closes: pin the build toolchain to TypeScript 6.x. If you want TS 7 speed for checking, run it as a separate `typecheck` script rather than as the compiler `nest` invokes. Re-check the issue before writing this into a project — it is the single most likely fact on this page to have changed.

## Recommended additional strictness

Not required by Nest, but they turn whole categories of the traps in these rules into compile errors:

```jsonc
{
  "strict": true,
  "noUncheckedIndexedAccess": true,     // Record lookups become `| undefined`
  "noImplicitOverride": true,
  "exactOptionalPropertyTypes": true
}
```

`noUncheckedIndexedAccess` is worth calling out: it widens every `Record` index access to `| undefined`, which forces a `?? fallback` on lookup tables. Those fallbacks are type artifacts, not real gaps — write them and move on rather than casting the type away.
